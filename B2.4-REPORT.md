# Phase 05-B2.4 — Security Hardening & QA

## Scope

- Central redaction for logger messages and structured fields (credential-shaped strings, sensitive property names, and explicitly supplied secret values).
- Safe client error mapping: unexpected errors become generic 500 responses; 5xx AppError messages/details/headers are not exposed.
- Production guard rejects missing/placeholder client tokens and `LOG_LEVEL=debug`.
- No new runtime dependencies or environment variables.

## Integration points

- `src/index.js` invokes the production guard after configuration/auth loading and supplies the client token to the logger redactor.
- `src/infrastructure/http/server.js` uses the safe error mapper and bounded error description for logs.

## Tests

Four Node.js built-in test files are included: `redact.test.js`, `loggerRedaction.test.js`, `errorResponse.test.js`, and `productionGuard.test.js`. They are discovered by the existing `node --test test/*.test.js` script.

**Test status: NOT RUN HERE.** Per project workflow, GitHub Actions must execute the full suite on Node 20 and Node 22 after the branch is pushed and a pull request is opened. No PASS claim is made in this report.

## Compatibility notes

- Existing `createLogger(level, write)` callers remain valid; the optional third argument is additive.
- Production token minimum length is unchanged to avoid invalidating existing deployment tokens.
- Production CORS `http://` entries are not newly prohibited; use HTTPS origins for public production clients.
- No provider integration, Gemini key loading, hosting deployment, or Android integration is included.

## Operational note

If the hosting environment currently sets `LOG_LEVEL=debug`, change it to `info`, `warn`, or `error` before deploying this phase. Never put real credentials in the repository or ZIP.
