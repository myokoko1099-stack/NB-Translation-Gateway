## Implemented

- **IP-based rate limiter** (`src/infrastructure/http/rateLimiter.js`): in-memory, fixed window, one small record per client key.
- **Configuration** (non-secret, in `loadConfig`, defaults in `profiles.js`):
  - `GATEWAY_RATE_LIMIT_MAX` — default 60, range 1–100000
  - `GATEWAY_RATE_LIMIT_WINDOW_MS` — default 60000, range 1000–3600000
  - `GATEWAY_TRUSTED_PROXY_HOPS` — default 0, range 0–10 (**added beyond the two requested variables**, see Decisions)
  - Invalid values stop startup with a message naming the variable and the allowed range; the offending value is never echoed; all problems are reported together.
- **429 response**: `{"error":{"code":"RATE_LIMITED","message":"Too many requests.","requestId":…}}` with `Retry-After` (integer seconds, never 0), `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, and `Connection: close`. Successful (and other post-limiter) responses also carry the three `RateLimit-*` headers.
- **Order of checks** (`server.js`): route → method → **authentication → rate limit** → body parsing/validation → service/provider. A rate-limited request never reaches the handler, so the **provider is never called**.
- **Client IP** (`clientIp.js`): TCP peer address only. `X-Forwarded-For` is ignored unless the operator sets `GATEWAY_TRUSTED_PROXY_HOPS=N`; then the N-th entry from the right (the one appended by the trusted proxy) is used, earlier (client-supplied) entries are ignored, and a missing/short/invalid header falls back to the peer address. IPv4-mapped IPv6 is normalised to IPv4; other IPv6 addresses are keyed by their /64 prefix.
- **Cleanup / memory protection**: expired records are removed by an unref'd periodic sweep (interval = min(window, 60 s)) and before inserting when the store is full; records are kept in expiry order so a sweep stops at the first live record; hard cap of 10,000 keys — when still full, **new** keys are rejected (fail closed) and live records are never evicted; the timer is stopped when the server closes.
- `GET /health` is not rate limited and unchanged.
- Logs record only `rate limit exceeded` with the request id — no IP address, header or token.

## Decisions (please review)

1. **Authentication before rate limiting.** Only requests with a valid token create or consume limiter records, so unauthenticated traffic cannot fill limiter memory or exhaust a legitimate client's budget. Trade-off: failed-token guessing is not throttled (see Security Risks).
2. **`GATEWAY_TRUSTED_PROXY_HOPS` added.** Without it, a deployment behind a hosting proxy would see every client as the proxy's IP and share one bucket. Default 0 keeps "never trust proxy headers" as requested; trusting is explicit opt-in.
3. **Fixed window** (simple, O(1) memory per key) rather than sliding window.
4. Only `POST /v1/translate` is limited. Requests that fail validation (400) still count, since they reach the limiter.
5. IETF-draft header names (`RateLimit-*`) are used; no `X-RateLimit-*` aliases.

## Security Risks

- **Token guessing is not throttled.** Because authentication runs first, wrong-token requests are rejected with 401 without limiter involvement. Mitigation: use a long random `GATEWAY_CLIENT_TOKEN` (e.g. ≥32 random characters). A separate failed-auth limiter would be a later phase.
- **Proxy misconfiguration.** `GATEWAY_TRUSTED_PROXY_HOPS` > 0 while the server is directly reachable (or with the wrong count) lets clients spoof their identity and evade limits. Behind a proxy with the default 0, all clients share one bucket (self-inflicted lockouts).
- **Key-store exhaustion by authenticated clients.** With 10,000 live keys, new client IPs are rejected until records expire. Needs a valid token and many source addresses; in dev/test with no token configured it is reachable by anyone (production requires a token).
- **Shared identities.** NAT / carrier-grade NAT users share one IPv4 budget; all hosts in one IPv6 /64 share one budget.
- **Fixed-window burst.** A client can send up to 2× the limit across a window boundary.
- State is not persisted, so a restart clears all counters.

## Known Limitations

- **Single-instance only.** Counters live in this process's memory: they are lost on restart and are not shared between instances. Running N instances multiplies the effective limit by about N and each instance counts separately. Distributed limiting (shared store) is intentionally not implemented.
- Only per-IP limiting; no per-token or per-route limits.
